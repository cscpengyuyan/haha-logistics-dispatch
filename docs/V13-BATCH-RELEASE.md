# V13 正式批量 F04 签发

入口：`POST /api/ops/dispatch-batches/release`。仅 `admin`、`dispatch`。服务端与公开浏览器使用同一 `batch_release.py`；公开环境仍是本浏览器隔离演练库。

请求为 `{"idempotency_key":"本次签发的唯一重试编号","items":[...]}`。每个 item 显式包含 `order_id`、当前 `version`、`action`（只能为 `dispatch` 或 `station_release`）以及该动作原本所需的全部参数：实际司机/承运、已核路线 ID/版本、F04 引用、批准费用、分支交接材料等。**每票均须提供完整十二项 `checks` 的实际凭据。** 工具不生成、复制或补齐任何业务凭据。

批次须为 1–200 个唯一订单。未知字段、空值、重复订单、无效动作/版本会拒绝。每票使用原 `core.preflight` 与 `core.apply_action`；原合同、站内实收、库存、资源时段、授权、路线版本和岗位门禁全部保留。`station_release` 也强制十二项；原始请求存入批次审计以保留各票新凭据。

可选同时提供 `plan_id` 与 `plan_version`。关联计划必须当前版本已采用、校验通过、无未排订单；批次订单集合必须与计划完整一致，每票使用该计划实际采用的路线或承运商委托。不能通过关联计划跳过原单核验，也不能带另一条路线或临时 direct_plan 替换计划。自提仍走独立仓口交接，不能在本接口冒充配送签发。

全批共享 SAVEPOINT。任一票失败时，前面已经发生的订单状态/版本、gate 授权和提货号、route_bookings、事件、路线与幂等凭证全部回滚。即使上层捕获异常后提交外层事务也不会留下部分签发。已有外层事务不会被本模块主动提交；独立调用则取得 SQLite `BEGIN IMMEDIATE` 写锁。

成功响应含 `batch` 与逐票 `orders`，返回原服务实际生成的签发版本和提货号。相同操作者、相同 `idempotency_key`、完全相同请求重试返回原响应；同键异请求为 `409 IDEMPOTENCY_CONFLICT`。失败不占用重试键。批次状态 `issued` 表示已签发，**不表示仓库已验放、车辆已离场或客户已签收**。

证据：`tests/test_v13_batch_release.py` 于 2026-11-02 通过6项测试（9.894秒）。使用真实 SQLite、业务API、两张 F04 和 HTTP 并发；分别在第二票缺 `papers`、第二车次争抢相同车辆/班组时，SQL轨迹证明第一票已写入后完整回滚。另验证同路线两票并发重试只签一次、同键异payload、操作者隔离、计划关联、输入门禁及外层事务回滚。此测试不宣称已经完成200票正式批量性能验收或所有二程组合回归。
